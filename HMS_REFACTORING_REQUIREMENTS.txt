HOSPITAL MANAGEMENT SYSTEM (HMS)
ENTERPRISE UX, USABILITY & ARCHITECTURE REFACTORING REQUIREMENTS

Version: 1.0
Date: 2026-08-08
Purpose: Guide AI coding agents and engineering teams in refactoring an existing Hospital Management System into a scalable, usable, safe, role-based enterprise HMS.

======================================================================

1. MISSION
   ======================================================================

Refactor the existing HMS into a modern, enterprise-grade healthcare
application that is:

* Easy and fast for healthcare professionals to use.
* Organized around real hospital workflows rather than backend modules.
* Patient-centric.
* Role-specific.
* Consistent across all modules.
* Accessible and responsive.
* Safe for clinical workflows.
* Auditable.
* Scalable.
* Maintainable.
* Extensible.
* Suitable for desktop, tablet, and mobile workflows where appropriate.

IMPORTANT:

This is a REFACTORING project, not an automatic rewrite.

Existing working functionality must NOT be removed merely because it is
implemented differently from the requirements in this document.

Before changing an existing feature:

1. Understand its current behavior.
2. Identify dependencies.
3. Preserve business rules unless they are demonstrably incorrect.
4. Improve the implementation without unnecessarily breaking existing
   workflows.
5. Preserve existing data.
6. Preserve existing APIs unless a migration strategy exists.
7. Add tests around existing critical behavior before major refactoring.

Coding agents MUST inspect the existing application before making major
architectural decisions.

======================================================================
2. PRIMARY PRODUCT PRINCIPLE
============================

The HMS must be designed around:

```
USER -> TASK -> PATIENT -> WORKFLOW
```

and NOT:

```
DATABASE TABLE -> MODULE -> CRUD SCREEN
```

The backend may remain modular, but the user experience must feel like
one coherent hospital system.

A user should not have to understand the internal architecture of the
software in order to perform a hospital workflow.

======================================================================
3. NON-NEGOTIABLE UX PRINCIPLES
===============================

3.1 Patient identity must always be obvious.

3.2 The current patient context should remain visible throughout clinical
workflows.

3.3 Common workflows must require the minimum reasonable number of steps.

3.4 Critical information must not be hidden behind unnecessary navigation.

3.5 Users must always understand:

```
- What patient they are viewing.
- What they are doing.
- What has happened.
- What needs attention.
- What happens next.
```

3.6 Do not expose backend complexity unnecessarily.

3.7 Do not use color as the only way to communicate status.

3.8 Avoid unnecessary modal dialogs.

3.9 Avoid unnecessary confirmation dialogs.

3.10 Preserve work during interruptions.

3.11 Errors must explain:

```
- What happened.
- Why it happened when useful.
- What the user can do next.
```

3.12 The system should favor task completion over information display.

3.13 The interface must be consistent across modules.

3.14 Critical clinical workflows must be designed for safety.

3.15 Real healthcare users must be involved in usability validation.

======================================================================
26. ALERTS
==========

Alerts must have severity.

Suggested hierarchy:

```
CRITICAL
IMPORTANT
WARNING
INFORMATION
```

Do not use the same visual treatment for all alerts.

Avoid alert fatigue.

An alert that does not require attention should not interrupt the user.

======================================================================
27. ERROR HANDLING
==================

Never expose raw technical errors to end users.

Bad:

```
500 Internal Server Error
```

Better:

```
We couldn't save the prescription.

Your changes have not been submitted.
Please try again.

[Try Again]
```

Technical details should be available to logs/engineering tools, not
unnecessarily exposed to users.

======================================================================
28. FORM DESIGN
===============

Forms must:

* Have clear labels
* Show required fields
* Validate appropriately
* Preserve entered data after recoverable errors
* Provide meaningful validation messages
* Group related fields
* Avoid unnecessary fields
* Support keyboard navigation
* Avoid unnecessary confirmation dialogs

Do not make users enter information the system already knows.

======================================================================
29. LOADING STATES
==================

Every asynchronous workflow should have a meaningful loading state.

Avoid blank screens.

Use:

* Skeletons
* Progress indicators
* Loading text
* Disabled action states where appropriate

Never allow users to wonder whether an action is still processing.

======================================================================
30. EMPTY STATES
================

Empty states must explain the situation.

Example:

```
No pending laboratory orders.

All current orders have been completed.
```

Avoid generic:

```
"No data."
```

* Unsaved-work warnings

Users should not lose significant work because they temporarily leave a screen.

===============

Important actions must be auditable.

Record where appropriate:

* User
* Action
* Entity
* Patient
* Timestamp
* Previous state
* New state
* Reason where required
* Source/context

Examples:

* Patient record changes
* Clinical note changes
* Prescription changes

======================================================================
41. DATA INTEGRITY
==================

Never compromise existing patient data during refactoring.

Before database migrations:

1. Backup.
2. Test migration against a copy.
3. Validate record counts.
4. Validate relationships.
5. Validate critical clinical data.
6. Test rollback/recovery.
7. Only then deploy.

Never silently delete or overwrite historical clinical information.

======================================================================
42. DATABASE REFACTORING
========================

Database changes must be incremental.

Avoid:

* destructive migrations
* unnecessary table rewrites
* duplicated sources of truth
* inconsistent identifiers
* storing derived data without a reason
* hardcoded business rules in database structures

Prefer:

* normalized core data where appropriate
* explicit relationships
* indexes for high-volume queries
* immutable/auditable clinical history where required
* migration scripts
* rollback strategy

======================================================================
43. BUSINESS LOGIC
==================

Business rules should not be duplicated across:

* frontend
* backend
* database
* background jobs

Where practical, centralize important business rules.

Frontend validation improves UX.

Backend validation enforces correctness.

Never rely exclusively on frontend validation.

45. CRITICAL WORKFLOW ACCEPTANCE TESTS
======================================

The following scenarios must be executable end-to-end.

SCENARIO A - REGISTER PATIENT

```
Register patient
-> Generate/assign patient identifier
-> Verify identity
-> Create record
-> Patient becomes searchable
```

SCENARIO B - DOCTOR CONSULTATION

```
Search patient
-> Open patient
-> Review overview
-> Review history
-> Review vitals
-> Create consultation note
-> Record diagnosis/problem
-> Create orders/prescription
-> Sign/finalize
-> Audit event recorded
```

SCENARIO C - LAB

```
Create order
-> Collect sample
-> Receive sample
-> Process
-> Enter result
-> Validate
-> Make result available
-> Notify/requeue appropriately
```

SCENARIO D - PHARMACY

```
Prescription created
-> Prescription enters pharmacy queue
-> Pharmacist reviews
-> Pharmacist dispenses
-> Stock updated
-> Dispensing recorded
-> Audit recorded
```

SCENARIO E - ADMISSION

```
Admission request
-> Assign ward
-> Assign bed
-> Update patient location
-> Record admission
-> Patient appears in ward workflow
```

SCENARIO F - DISCHARGE

```
Discharge initiated
-> Required documentation completed
-> Orders/relevant tasks resolved
-> Billing handled as appropriate
-> Discharge recorded
-> Bed becomes available
-> Patient status updated
```

46. AGENT REFACTORING RULES
===========================

Coding agents MUST follow these rules.

RULE 1:

Do not rewrite large parts of the system without first inspecting them.

RULE 2:

Do not delete working functionality without explicit justification.

RULE 3:

Do not change database structures unnecessarily.

RULE 4:

Do not introduce a new framework merely because it is preferred.

RULE 5:

Prefer incremental refactoring.

RULE 6:

Keep commits/changes logically isolated.

RULE 7:

After significant changes, run relevant tests.

RULE 8:

Fix regressions before continuing.

RULE 9:

Do not hide errors to make tests pass.

RULE 10:

Do not hardcode data merely to make UI demonstrations work.

RULE 11:

Do not create fake backend behavior for production workflows.

RULE 12:

Do not bypass authorization for convenience.

RULE 13:

Do not expose sensitive patient data in logs.

RULE 14:

Do not silently alter clinical history.

RULE 15:

Do not create duplicate components when an existing reusable component
can be improved.

RULE 16:

Prefer reusable abstractions when repetition is genuine.

RULE 17:

Avoid premature abstraction.

RULE 18:

Document architectural decisions that affect future development.

======================================================================
48. DEFINITION OF DONE
======================

A refactored feature is NOT considered complete merely because it compiles.

A feature is complete when:

* Existing required functionality still works.
* New requirements are implemented.
* Authorization is enforced.
* Validation exists.
* Error states exist.
* Loading states exist.
* Empty states exist.
* Responsive behavior is appropriate.
* Accessibility has been considered.
* Relevant tests pass.
* No obvious regression exists.
* UI follows the design system.
* Audit requirements are satisfied.
* Performance is acceptable.
* Documentation is updated where appropriate.

49. UX QUALITY GATES
====================

Before considering a workflow complete, ask:

PATIENT CONTEXT:

```
Is the patient identity obvious?
```

EFFICIENCY:

```
Can a trained user complete the workflow quickly?
```

COGNITIVE LOAD:

```
Is unnecessary information hidden?
```

ERROR PREVENTION:

```
Does the interface prevent predictable mistakes?
```

ERROR RECOVERY:

```
Can the user recover without losing work?
```

ACCESSIBILITY:

```
Can users operate the workflow without relying solely on color,
mouse interaction, or perfect vision?
```

CONSISTENCY:

```
Does this behave like the rest of the HMS?
```

SECURITY:

```
Can unauthorized users access or modify the data?
```

AUDIT:

```
Can important actions be traced?
```

PERFORMANCE:

```
Does this remain usable with realistic hospital data volumes?
```

* Search failure rate
* Task completion rate
* User-reported usability problems
* Page/API response time
* Error rate
* Alert dismissal rate

The objective is not simply to make the system prettier.

The objective is to make users:

```
FASTER
SAFER
MORE CONFIDENT
LESS FRUSTRATED
```

======================================================================
51. INFORMATION ARCHITECTURE
============================

The application should conceptually separate:

PATIENTS

```
Patient records and patient-centric workflows.
```

MY WORK

```
Tasks requiring the current user.
```

CLINICAL

```
Clinical workflows and documentation.
```

OPERATIONS

```
Appointments, queues, admissions, beds, departments.
```

PHARMACY

```
Medication and pharmacy operations.
```

LABORATORY

```
Laboratory operations.
```

RADIOLOGY

```
Imaging operations.
```

BILLING

```
Charges, invoices, payments, insurance.
```

INVENTORY

```
Stock and procurement.
```

REPORTS

```
Analytics and reporting.
```

ADMINISTRATION

```
Configuration, users, roles, permissions.
```

The exact navigation may differ based on the existing application, but the
principle should remain.

======================================================================
52. PATIENT-CENTRIC NAVIGATION RULE
===================================

When a user is inside a patient context, navigating between relevant patient
activities should not feel like leaving the patient.

Example:

```
Patient
   |
   +-- Overview
   +-- Notes
   +-- Orders
   +-- Medications
   +-- Labs
   +-- Imaging
   +-- Procedures
   +-- Admissions
   +-- Documents
```

The current patient should remain identifiable throughout the workflow.

======================================================================
53. DESIGN FOR POWER USERS
==========================

Healthcare professionals may use the system for many hours every day.

Support where appropriate:

* Keyboard navigation
* Keyboard shortcuts
* Fast search
* Autocomplete
* Recent patients
* Recent actions
* Frequently used options
* Smart defaults
* Batch operations where safe
* Quick filters
* Persistent preferences

Do not sacrifice simplicity for power-user features.

Use progressive disclosure.

======================================================================
54. MOBILE / TABLET UX
======================

Touch interfaces must provide:

* Large enough touch targets
* Clear primary actions
* Minimal typing where possible
* Appropriate sticky actions
* Readable text
* Simple navigation
* Offline/error awareness where applicable

Do not force users to interact with tiny desktop controls on mobile.

======================================================================
55. OBSERVABILITY
=================

Engineering teams must be able to diagnose failures.

Implement appropriate:

* Structured logging
* Error tracking
* Performance monitoring
* API monitoring
* Database monitoring
* Background-job monitoring

Logs must not unnecessarily contain sensitive patient information.

1. What was inspected.
2. What was changed.
3. Why it was changed.
4. What existing behavior was preserved.
5. What tests were added/updated.
6. What tests were run.
7. Any migration required.
8. Any known limitations.
9. Any follow-up work recommended.

======================================================================
58. FINAL PRODUCT STANDARD
==========================

The finished HMS should NOT feel like:

```
"A collection of CRUD screens for hospital databases."
```

It should feel like:

```
"A unified digital operating system for the hospital."
```

A doctor should be able to understand a patient's situation quickly.

A nurse should immediately know what needs to be done.

A receptionist should process patients without unnecessary navigation.

A pharmacist should process prescriptions safely and efficiently.

A laboratory worker should understand the processing queue immediately.

An administrator should see operational information without being exposed
to unnecessary clinical complexity.

A patient should be able to interact with patient-facing functionality
without understanding the hospital's internal architecture.

======================================================================
59. GOLDEN RULE
===============

Every feature should answer three questions:

```
WHO is using this?

WHAT are they trying to accomplish?

WHAT information/action do they need RIGHT NOW?
```

If a proposed UI element does not help answer or accomplish those questions,
question whether it belongs on the screen.

======================================================================
60. AGENT INSTRUCTION
=====================

When implementing this specification:

1. Inspect the existing codebase first.
2. Build an inventory of existing functionality.
3. Identify reusable code before creating new code.
4. Identify risks before changing architecture.
5. Preserve working business functionality.
6. Refactor incrementally.
7. Improve UX through reusable patterns.
8. Prioritize patient safety and data integrity.
9. Test critical workflows continuously.
10. Never trade correctness for visual polish.
11. Never trade security for convenience.
12. Never trade clinical safety for speed.
13. Never silently destroy existing data.
14. Never introduce fake functionality in production code.
15. When requirements conflict with existing behavior, document the conflict
    and choose the safest migration path.
16. Prefer small, verifiable changes over massive rewrites.
17. Treat this document as the product/UX direction, not as permission to
    blindly modify every part of the existing application.

The goal is a progressive transformation of the existing HMS into a
cohesive, patient-centric, workflow-oriented enterprise healthcare
platform.
